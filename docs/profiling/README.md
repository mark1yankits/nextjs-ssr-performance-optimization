# Профілювання backend (Node.js `--prof`)

## Як відтворити

```bash
cd backend
npm run build
node --prof dist/server.js &

cd ../load-tests
k6 run backend-list.js
k6 run backend-detail.js

# зупинити сервер (Ctrl+C або kill), потім обробити лог:
cd ../backend
node --prof-process isolate-*.log > ../docs/profiling/backend-prof-summary.txt
```

Повний оброблений вивід — [`backend-prof-summary.txt`](./backend-prof-summary.txt).

## Умови

Профіль знято під час прогону обох k6-тестів (`backend-list.js`, `backend-detail.js`,
кеш увімкнено) — тобто типове навантаження production-режиму, ~11 000 запитів за 60с.

## Результати ([Summary](./backend-prof-summary.txt#L552))

| Категорія | % тіків |
|---|---|
| **Unaccounted** (очікування на I/O — мережа до Neon/Redis, epoll) | 76.3% |
| **JavaScript** (виконання коду) | 23.7% |
| **GC** (збирання сміття) | 2.3% |
| **C++** (нативні аддони) | 0.0% |

**Головний висновок:** цей backend — **I/O-bound, не CPU-bound**. Понад три чверті
часу процес узагалі не виконує JS-код — він чекає на відповідь від Redis або Neon.
Це прямо пояснює, чому саме кешування (усунення мережевого I/O) дало найбільший
приріст продуктивності серед усіх оптимізацій (Крок 2, `performance-report.md`), а не
щось на кшталт оптимізації алгоритмів чи паралелізації обчислень — обчислювати
тут майже нічого.

## Найгарячіші шляхи виклику ([Bottom up (heavy) profile](./backend-prof-summary.txt#L563))

Серед тих 23.7% часу, що йде на JavaScript, найбільше "гарячих" тіків припадає на:

1. **`morgan` (логування запитів)** — `logRequest`/`writeOrBuffer` у сумі забирають
   помітну частку JS-часу (запис кожного HTTP-запиту в stdout синхронно в hot path).
   **Практичний висновок:** у production варто або вимкнути `morgan("dev")`, або
   перемкнути на асинхронний/буферизований логер (напр. `pino` з `pino-http`), або
   логувати лише помилки — особливо під високим навантаженням.
2. **`ioredis` парсинг відповідей** (`transformReply`/`redis-parser`) — очікувано:
   кеш обробляється майже на кожен запит, і десеріалізація Redis-протоколу займає
   помітну частку JS-часу. Це "корисна" робота — плата за виграш від кешування.
3. **`pg` (запити до Postgres)** — практично не з'являється в топі гарячих шляхів,
   бо з увімкненим кешем більшість запитів взагалі не доходять до БД. Це підтверджує
   ефективність cache-aside стратегії: Postgres/Neon навантажується лише на cache miss.

## Що б я оптимізував далі (на основі профілю)

1. Прибрати/зменшити логування `morgan` у production або зробити його асинхронним.
2. Розглянути `JSON.stringify`/`parse` як потенційне вузьке місце при більших пейлоадах
   (не проявилось помітно на 5.7КБ відповідях, але вартувало б перевірити з більшими
   `limit`).
3. Дані з профілю підтверджують: подальша "мікрооптимізація" JS-коду дасть значно
   менший ефект, ніж уже впроваджене кешування — I/O лишається домінантним фактором.
