# Звіт з продуктивності

Усі числа нижче отримані реальними прогонами (k6, Lighthouse) на цьому проєкті,
а не оцінені теоретично. Умови: MacBook (Apple Silicon), backend на Neon
(віддалена БД, не localhost), Redis у Docker локально, Next.js — production-білд
(`npm run build && npm run start`).

## 1. SQL: вибір лише потрібних полів

Таблиця `articles` містить важке поле `content` (середня довжина — **2395 символів**
на статтю, виміряно напряму в Neon: `SELECT avg(length(content)) FROM articles`).

| Запит | Обсяг відповіді (20 статей) |
|---|---|
| Поточний API (`content` виключено зі списку) | **5.7 КБ** |
| Гіпотетичний `SELECT *` (з `content`) | ≈ 53 КБ (5.7 КБ + 20 × 2395 симв.) |

Виключення `content` зі списку зменшує обсяг відповіді приблизно **у 9 разів** —
критично для мобільних мереж і TTFB під навантаженням, оскільки менше даних
потрібно серіалізувати на сервері й передати по мережі.

## 2. Redis-кешування: з кешем / без кешу

Навантаження: k6, 20 VU, 30с. Кеш вимикався прапорцем `DISABLE_CACHE=true`
(однаковий код, однаковий сценарій — єдина відмінність: кеш увімкнено/вимкнено).

| Ендпоінт | Кеш | p95 latency | Throughput | cache_hit_rate |
|---|---|---|---|---|
| `GET /api/articles` | увімкнено | **10.5 мс** | **182 req/s** | 99.6% |
| `GET /api/articles` | вимкнено | 442 мс | 37 req/s | 0% |
| `GET /api/articles/:slug` | увімкнено | **19.5 мс** | **174 req/s** | 99.6% |
| `GET /api/articles/:slug` | вимкнено | 177 мс | 75 req/s | 0% |

**Висновок:** кеш зменшує p95-затримку у **42 рази** (список) і **9 разів** (деталі),
збільшуючи пропускну здатність у 5 та 2.3 рази відповідно. Розрив такий значний саме
через мережеву затримку до Neon (хмарна БД, а не localhost) — це типовий реальний
сценарій, коли БД територіально віддалена від бекенду.

Повні дані й команди відтворення — [`../load-tests/README.md`](../load-tests/README.md).

## 3. Стратегії рендерингу Next.js: SSR / ISR / Streaming

### 3.1. Пропускна здатність під навантаженням (k6, 20 VU, 30с, production-білд)

| Сторінка | p95 latency | Throughput |
|---|---|---|
| `/ssr` | 44 мс | 142 req/s |
| `/isr` | 9 мс | 193 req/s |
| `/streaming` | 3.1 с | 9 req/s (навмисна затримка 2с) |

### 3.2. Lighthouse (Core Web Vitals), одиночний запит

Виміряно з `--throttling-method=devtools` (без симуляції мережі — інакше Lighthouse
за замовчуванням використовує "lantern"-модель, яка не відображає реальні
серверні затримки на кшталт навмисної паузи в `/streaming`). Сирі звіти — у
[`./lighthouse/*.json`](./lighthouse).

| Сторінка | TTFB | FCP | LCP | TTI |
|---|---|---|---|---|
| `/ssr` | 21 мс | 49 мс | 49 мс | 49 мс |
| `/isr` | 9 мс | 40 мс | 40 мс | 40 мс |
| `/streaming` | 16 мс | 54 мс | 54 мс | **2033 мс** |

**Інтерпретація:**

- **ISR** — найшвидший варіант за всіма метриками: сторінка вже згенерована й
  віддається зі статичного кешу без звернення до backend під час запиту.
- **SSR** трохи повільніший за ISR (рендеринг + мережевий запит до API при кожному
  відкритті), але зі включеним Redis-кешем на backend різниця невелика.
- **Streaming** має практично такий самий швидкий **FCP/LCP**, як і інші сторінки
  (браузер починає малювати контент одразу, не чекаючи повільний блок) — але **TTI**
  чітко показує реальну затримку 2с, коли Suspense-блок дозавантажується. Це і є
  суть стрімінгу: користувач бачить сторінку одразу, хоча "повна готовність"
  настає пізніше. LCP тут не зловив список статей як найбільший елемент (він
  складається з багатьох дрібних `<li>`, жоден з яких не перевищив по площі вступний
  параграф) — показовий приклад того, що LCP не завжди відображає весь досвід
  завантаження і його варто доповнювати TTI/TBT.

## 4. Загальні висновки

1. **Найбільший ефект дає Redis-кеш** для запитів до віддаленої БД — на порядок
   менша затримка, вища пропускна здатність, і чим "далі" БД (мережево), тим
   виграш більший.
2. **Вибір лише потрібних полів у SQL** — дешева, але суттєва оптимізація: у
   рази менший обсяг трафіку без жодних архітектурних змін.
3. **ISR — найкращий вибір для контенту, що рідко змінюється** (списки, каталоги):
   комбінує швидкість статики зі свіжістю через фонову ревалідацію.
4. **Streaming SSR — не про пропускну здатність, а про сприйняту швидкість**:
   доцільний, коли частина даних повільна, а решту сторінки можна показати
   негайно (наприклад, шапка/навігація швидко, важкий блок — пізніше).
5. **SSR** (`force-dynamic`) варто лишати для даних, які справді мають бути
   актуальними на кожен запит (персоналізований контент, дані що часто змінюються).
